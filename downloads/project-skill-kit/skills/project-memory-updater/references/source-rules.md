# 來源判斷規則

## 專案範圍

- 只處理使用者指定的單一專案。
- 依專案名稱、會議主題、正文、決策、待辦、具體工作事項與前後文判斷相關性。
- 相同人物、日期、寄件者或 LINE 群組成員不代表同一專案。
- 正式納入前逐項檢查：拿掉人物姓名後，事情本身與上下文是否仍明確屬於指定專案？
- 明確無關的資料排除；無法確認歸屬的資料列為「需要人工確認」。

## 允許來源與既有工作記憶

- 只處理本次允許來源；未經指定的來源不搜尋、不讀取，也不納入結果。
- 本次新增事實只能來自本次允許來源、本次指定日期範圍，且通過專案相關性判斷的資料。
- 不得用過去對話、模型記憶、其他聊天、常識推測、同一人物的舊工作或其他專案資訊補入新事實。
- 既有工作記憶只能用於同一專案內的前後比較，不能提供新增事實。
- 跨更新期間發生明確變更時，保留舊版本 → 新版本，不直接刪除較早的有效紀錄。

## 日期範圍

- 只納入本次指定日期範圍內的來源紀錄。
- 以執行當下的實際系統日期為界。指定結束日晚於當日時，未來部分標為「該期間尚未發生」，不可寫成查無資料。
- 來源的建立、會議或郵件日期用來判斷是否落在範圍內；內容中的期限則保留為專案資訊，不等於來源日期。

## Google Drive、Google Meet 與 Tactiq

- 本次允許 Google Drive 時，在其中尋找日期範圍內可能相關的 Tactiq／Google Meet 紀錄。
- 必須打開文件並實際讀取完整內容，不可只依檔名、搜尋摘要或片段判斷。
- 會議紀錄視為「會議當下版本」，不是永遠有效的最終版本。
- 搜尋可以廣找候選，但只有讀取正文並通過專案相關性判斷的內容才能納入。

## Gmail 與 LINE 紀錄

- 本次允許 Gmail 時，在其中尋找日期範圍內主旨包含 `[LINE紀錄]` 的候選郵件。
- 必須打開郵件並實際讀取正文，不可只依主旨或搜尋摘要判斷。
- 使用者直接貼上的 LINE 紀錄依相同規則處理。
- 後續 LINE 紀錄若明確說明變更，可以更新較早的會議當下版本。

## 來源狀態

每個允許來源分別標記：

1. 已讀取且找到相關資料。
2. 已成功存取，但指定已發生期間內未找到相關資料。
3. 目前無法存取此來源。
4. 該期間尚未發生。

權限、連線或工具錯誤不得被描述為沒有資料。無法存取時，要求使用者提供、上傳或貼上來源內容。

## 來源優先順序

沒有固定的「LINE 一定高於會議」或「較晚一定高於較早」順序。來源是否更新舊版本，取決於時間、專案相關性與語意是否明確。

「較晚」不代表一定正確。只有後續內容明確表示「修改」「改成」「延後」「取消」「改由」「改為」等版本更新，才以新版本更新舊資訊，並保留舊版本 → 新版本的變更紀錄。

「候選」「暫定」「考慮」「建議」「可能」「預計」不算已確認更新。

## 版本更新規則

1. 先建立每個來源在當時記錄的版本。
2. 依來源時間排序，但不單憑時間決定真偽。
3. 找出明確修改舊決策、期限、負責人或狀態的句子。
4. 將明確新版本列入最新已確認決策或待辦。
5. 在決策變更保留舊版本 → 新版本，並盡量標示日期與來源。

## 來源衝突規則

- 兩個來源不同，但沒有足夠證據判斷哪個是新版時，不得自行選擇。
- 把差異列入「衝突提醒」，說明各來源內容、日期與缺少的判斷依據。
- 需要使用者決定或補充資料的項目，同時列入「需要人工確認」。
